User flowPMFI uses asynchronous deposit and redemption requests.Users do not receive shares or USDC immediately when they submit a request. Requests are processed through the vault’s report-based accounting system.Deposit pricingDeposits are processed at the higher of current PPS or the initial $1.00 PPS.depositPPS = max(currentPPS, INITIAL_PPS)This means users deposit at:$1.00 PPS if current PPS is below $1.00current PPS if current PPS is above $1.00Shares are minted as:shares = depositAmount × NAV_PRECISION / depositPPSThis prevents below-$1 deposit entry and protects existing holders from dilution.Deposit flow1. User submits deposit requestThe user submits a deposit transaction with USDC.requestDeposit(uint256 assets, address receiver)Requirements:assets >= MIN_DEPOSIT_USDC
receiver != address(0)
vault cap is not exceededThe vault transfers USDC from the user and records a pending deposit request.2. Report processes the deposit requestA valid report processes pending deposit requests.The deposit is priced at:depositPPS = max(currentReportPPS, INITIAL_PPS)The request becomes claimable.3. Keeper automation claims sharesAfter the request becomes claimable, keeper automation may call:autoClaimDeposits(uint256[] requestIds)Shares are minted to the receiver:shares = assets × NAV_PRECISION / depositPPS4. Manual fallbackIf automation does not complete the claim, the request owner may call:claimDeposit(uint256 requestId, address receiver)Redeem flow1. User submits redemption requestThe user submits a redemption transaction with pARB shares.requestRedeem(uint256 shares, address receiver)The vault transfers the user’s pARB shares into the vault and records a pending redeem request.Redemptions are priced at the current official PPS.The redeem amount is calculated using current official PPS:lockedAssets = shares × officialPPS / NAV_PRECISION2. Report processes the redeem requestA valid report processes pending redeem requests in FIFO order if sufficient spendable vault liquidity is available.The request becomes claimable when the vault has enough spendable USDC.3. Keeper automation pays USDCAfter the request becomes claimable, keeper automation may call:autoClaimRedeems(uint256[] requestIds)The vault transfers claimable USDC to the receiver.4. Manual fallbackIf automation does not complete the claim, the request owner may call:claimRedeem(uint256 requestId, address receiver)Automated claim flowAfter a deposit or redeem request is processed by a report, PMFI may automatically claim it through keeper automation.For deposits, this means pARB shares can be automatically minted to the user’s receiver address after the request becomes claimable.For redemptions, this means claimable USDC can be automatically transferred to the user’s receiver address after the request becomes claimable.Users normally only need to submit:a deposit requestor a redemption requestThe rest of the flow may be completed automatically by PMFI keeper automation.Manual fallbackIf automation does not complete the claim, the request owner may still use the claim function directly where supported by the contract.Cancel stale requestIf a request remains pending longer than:MAX_REQUEST_AGE = 30 daysthe request owner can call:cancelRequest(uint256 requestId, bool isDeposit)For stale deposit requests, USDC is returned to the user.For stale redeem requests, locked pARB shares are returned to the user.
